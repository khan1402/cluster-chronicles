# Notes - cluster chronicles

What was built in each group, every problem that came up, and how it was fixed.
Format: **Did** (what was done), **Problem** (what went wrong), **Fix** (the
solution and why it works).

---

## Group 1: VM, cluster, app, storage

**Did:** Checked the Proxmox server: 369 GiB RAM, 40 threads, but only one
67.8 GB disk (about 48 GB thin pool for VMs). Disk, not RAM, is the limit.
**Fix (design):** VM 500 is a linked clone of template 9000 (shares the base
disk), disk with `discard` so deleted files return space to the pool, and every
data store gets a size or time limit.

**Did:** `create-vm.sh` (Proxmox) and `setup-cluster.sh` (VM): Minikube with the
Docker driver, ingress and metrics-server addons, Minikube as a systemd
service, nginx stream forwarder for ports 80/443/8443.
**Problem:** Minikube's node IP 192.168.49.2 exists only inside the VM; the
laptop and browser can't reach it.
**Fix:** nginx on the VM forwards ports 80, 443 and 8443 to the node, and
kubectl on the laptop uses `https://192.168.0.122:8443`.

**Did:** Namespaces with Pod Security levels, StorageClass `manual` and 5
hostPath PVs, backend/frontend Deployments, Services, ConfigMap, HPA, Ingress.
Images rebuilt as non-root (UID 10001); the frontend moved to port 8080
because a non-root process can't bind port 80.
**Problem:** Docker isn't installed in WSL, so images couldn't be built on the laptop.
**Fix:** The first images were built and pushed on the VM (copy the app
folder, `docker login`, build, push, `docker logout`). From Group 2 on,
Jenkins builds them with Kaniko.

**Problem:** After a VM reboot the page showed "Backend unreachable" for a moment.
**Fix:** No change needed - the frontend became Ready before the backend.
Readiness probes stop traffic to pods that aren't ready, and the message
disappeared once the backend was up.

## Group 2: Jenkins in the cluster

**Did:** Jenkins StatefulSet with PVC, JCasC, plugins from an init container,
two ServiceAccounts with RBAC, build pod with Kaniko/Trivy/k6, Jenkinsfile with
automatic rollback and Slack, secrets from `secrets.env`.

**Problem:** Jenkins went into `RunContainerError`.
**Fix:** The Secret was mounted at `/run/secrets`. In the Jenkins image
`/var/run` is a link to `/run`, so Kubernetes could no longer create
`/var/run/secrets/kubernetes.io/serviceaccount` (the ServiceAccount token).
The Secret moved to `/var/jenkins_secrets`.

**Problem:** JCasC failed with "unresolved variable".
**Fix:** An edit had placed an extra `env` entry between `name` and `value`,
which produced a duplicate key. Secrets are now read as files with
`${readFile:/var/jenkins_secrets/...}`, and only the admin password stays an
environment variable.

**Problem:** The k6 stage failed with "process apparently never started".
**Fix:** k6 ran as UID 12345, which couldn't write the workspace `@tmp` folder
owned by UID 1000. The k6 container now runs as UID 1000 with `HOME=/tmp`.

**Did:** Builds #4 and #5 failed after deploy.
**Result:** Both rolled back automatically to the previous version and Slack
reported it - the rollback path was proven by a real failure. Build #6 deployed.

## Group 3A: monitoring and alerting

**Did:** kube-prometheus-stack via Helm, ServiceMonitor for the app, 10 alert
rules, Alertmanager routing to Slack, 3 Grafana dashboards generated by
`build-dashboards.py`, Ingresses for Grafana, Prometheus and Alertmanager.

**Problem:** The secrets script was run before the updated file was saved, so
the new Grafana and Alertmanager Secrets were missing.
**Fix:** Saved the updated `create-secrets.sh` and ran it again; it is
idempotent (`apply --server-side`).

**Problem:** Prometheus was in `CrashLoopBackOff`.
**Fix:** The Operator mounts the volume with a subPath `prometheus-db`, which
Kubernetes created as root; Prometheus runs as UID 1000. Set
`storageSpec.disableMountSubPath: true` and an init container chowns the folder.

**Problem:** After the restart demo, the PodFrequentRestarts RESOLVED message
came about 15 minutes late.
**Fix:** Not a bug: the rule counts restarts in a 15-minute window, so it only
clears once the old restarts leave the window, plus the Alertmanager group
interval. The alert text was improved to say how many restarts were counted.

## Group 3B: logging

**Did:** Elasticsearch StatefulSet (2 nodes), setup Job (ILM 3 days, index
template), exporter, Fluent Bit DaemonSet, Kibana, Kibana import Job with 3
dashboards.

**Problem:** No node logs arrived.
**Fix:** The journal on the Minikube node is at `/run/log/journal`, not
`/var/log/journal`. Fluent Bit's systemd input path and hostPath volume were changed.

**Problem:** FluentBitOutputErrors fired; Elasticsearch rejected lines with
`document_parsing_exception` (`app.trace_id`: long vs text).
**Fix:** `Merge_Log` parsed the JSON lines of every pod into one field, and
different tools (Kibana, Elasticsearch) use the same field name with different
types. JSON parsing now happens only for the `app` namespace (separate tail
input and filter); the broken daily index was deleted. Result: 0 errors.

**Problem:** Kibana panels stayed empty after the fix.
**Fix:** The browser tab still held the old data view field list. Refreshing
the data view's fields and reloading the page (F5) fixed it.

**Did:** Yellow test - scaled Elasticsearch to 1 node: FIRING after ~2 minutes,
RESOLVED after scaling back to 2.

## Group 3C: network policies, scripts, demos

**Did:** Tested that kindnet enforces NetworkPolicies (deny-all in a test
namespace blocked traffic), then applied 22 policies: default deny + allow lists.
**Result:** A test pod in `default` can no longer reach the backend or
Elasticsearch; the app, Jenkins builds, Prometheus targets and logging all keep
working (build #10 green, started by the push itself).

**Did:** `deploy-all.sh` (ordered, idempotent install) and `validate.sh`.
**Problem:** `validate.sh` hung at the network policy test.
**Fix:** The test pod was started with `kubectl run -i`, which attaches to the
terminal and waited for keyboard input inside the script. The pod now runs on
its own; the script waits for it to finish and reads its log.

**Problem:** Re-running `deploy-all.sh` fired FluentBitOutputErrors.
**Fix:** One DNS lookup timed out during the run; Fluent Bit retried and
succeeded 10 seconds later, no log lost. The rule fired on any retry, which is
too sensitive. It now fires on errors or given-up retries, or more than 5
retries in 5 minutes, for 2 minutes.

**Problem:** The server lost power (extension board switched off) without a shutdown.
**Fix:** Nothing broke: after power-on the VM and Minikube started by
themselves and `validate.sh` passed once Elasticsearch had recovered.

**Problem:** The disk demo filled the node to 82%, but NodeLowDiskSpace never fired.
**Fix:** Inside the Minikube node, `/` is an overlay filesystem, which
node-exporter skips by default, so the rule watching `mountpoint="/"` had no
data at all. The real disk shows up as `/var` (ext4). The rule and the Grafana
disk panel now watch `/var`. This bug would have stayed hidden without the demo.

**Problem:** A demo script failed with "namespace is being terminated".
**Fix:** `cleanup.sh` had just deleted the `demo` namespace. The scripts now
wait until an old `demo` namespace is fully gone before creating a new one.

**Problem:** Running the CPU and memory demos together made the cluster stop
responding (`TLS handshake timeout`, Prometheus page not loading, no Slack alert).
**Fix (immediate):** The VM was restarted from Proxmox and `cleanup.sh` removed
the demo pods.
**Fix (root cause):** Minikube's container had a 40 GB limit, but the node
reported the VM's 48 GB; the memory demo planned for 48 GB and pushed all pods
against the 40 GB limit, and Prometheus starved too. The VM now has 128 GB
and the Minikube container a 124 GB limit (`docker update`, also in
`create-vm.sh` / `setup-cluster.sh`). The demos are safe now: CPU is capped at
88% of the node with a CPU limit, memory aims at 91% with a memory limit,
both stop by themselves, and memory refuses to start while the CPU demo runs.

**Problem:** A snapshot "with RAM" locked the VM for a long time.
**Fix:** Saving 48 GB of RAM onto the small thin pool was slow and risky. The
task was stopped, then `qm unlock 500` and `qm delsnapshot 500 demo_fixes --force`.
Snapshots are taken without RAM.

**Problem:** After a cold start, Jenkins stayed in `Init` and `PodPendingTooLong`
fired for `jenkins-0`.
**Fix:** The plugin init container couldn't reach `updates.jenkins.io` while
the network was still coming up, and got stuck retrying. Deleting the pod
fixed it, and the plugins are now cached on the Jenkins disk (downloaded again
only when `plugins.txt` changes), so a restart needs no internet.
The alert was a real catch.

**Problem:** `memory.sh` refused to start: "CPU demo still running".
**Fix:** The finished CPU pod still existed with status `Completed`; the check
now looks for a pod that is actually `Running`.

**Note:** During the memory demo, ContainerMemoryNearLimit also fired for the
demo pod itself (94% of its own safety limit) - correct behaviour. Proxmox kept
showing ~94% memory after the demo while Grafana showed 5%: the hypervisor
counts RAM the VM has touched since boot (no ballooning), the VM's own numbers
are the real usage.

**Note:** The API server demo also made kube-state-metrics and the storage
provisioner restart several times (they lose their connection to the API
server), and `KubeAggregatedAPIDown` went to the `null` receiver. Expected side
effects; they cleared by themselves.

**Problem:** Build #17 failed in the smoke test and rolled back.
**Fix:** The new version worked, but all 6 requests went to one pod: the second
new pod had just become ready and ingress-nginx needed a few seconds to add it.
The smoke test now keeps sending requests (1 per second, up to 30) until a
second pod answers, and only fails if that never happens. Build #19 deployed.

**Problem:** The new "demo mode is off" check in `validate.sh` failed while demo
mode was off.
**Fix:** It counted every line with `for: 5m`, including a comment. It now
counts only indented rule lines.

**Result:** All 9 alerts and the HPA demonstrated (FIRING and RESOLVED in
Slack); `validate.sh` 53 passed, 0 failed.
